# Rinspace 表里世界需求

> 状态：需求、技术设计、任务 1–27 与生产切换已完成；联邦保持关闭。

## 1. 问题

Rinspace 当前把博客、书籍、问答、讨论、动态、标签和知识图谱放在同一个前端信息架构中。问答、讨论和动态的边界不够清楚，而首页、个人页和标签页又同时装载过多不同性质的内容。

Rinspace 希望形成同一站点的两个世界：以书籍、博客和知识为主的安静表世界，以及以短帖和实时互动为主的活跃里世界。里世界采用 Rinspace 的 Mastodon fork，但用户不应感受到第二套站点、第二个账号或第二张粉丝图。

## 2. 目标

1. 建立可分享、可刷新、可回退且不依赖隐式本地状态的表里世界模型。
2. 让 Logo 成为全站翻面动作，让 `Rinspace` 文字成为当前世界的首页动作。
3. 让本地账号、资料、头像、封面和关注关系在两个世界中保持同一身份、同一事实。
4. 保留 Mastodon 完整的本地社区能力，并在第一阶段提供个性化推荐与非个性化关注流，而不是只复制一个帖子列表；ActivityPub 联邦代码保留但第一阶段不对外启用。
5. 让表世界继续以博客、书籍和知识标签为主，并保留既有讨论、问答、动态入口。
6. 为标签建立知识对象与 hashtag 的明确绑定，保证标签导航不跨世界。
7. 让公开前端、Mastodon fork 和私有服务通过不可变版本与明确契约协作。
8. 在开放发帖、评论或推荐前建立适用于中国境内服务的账号、内容、个人信息和算法合规门禁，并把跨实例联邦留给未来独立评估。

## 3. 非目标

- 本期不删除讨论、问答、动态路由或历史数据。
- 本期不把博客、书籍、问答或讨论强制迁成 Mastodon Status。
- 本期不把所有 Rinspace 页面都虚构成有反面。
- 本期不把 Mastodon 嵌入 iframe。
- 本期不让浏览器直接持有私有服务凭据，也不把生产配置放入公开仓库。
- 本期不把 Gitea Star/Watch 的内容收藏与内容关注语义迁给 Mastodon。
- 本期不解析、抓取、接收或展示任何远端账号和帖子，不允许远端关注，不向其他实例投递，也不开放跨实例联邦发现。
- 本期不开放任何境内或境外实例联邦；未来启用必须另立规格、重新核查合规并由产品明确确认。
- 本期不修改 ActivityPub 对象 URI 来迎合网页可读 slug。
- 本期不要求 Logo 自身具有复杂翻转反馈；先完成行为、内容转场和可访问性。

## 4. 领域定义

- **表世界（outer）**：默认世界，以博客、书籍、知识标签和知识关系为主要内容。
- **里世界（inner）**：Mastodon 驱动的社交世界，以帖子、回复、repost、like、bookmark、媒体、列表、通知、个性化推荐和关注时间线为主要内容。
- **双面资源**：两个世界都存在且能稳定互相定位的同一资源。首批至少包括世界首页、本地账号和已绑定标签。
- **单面资源**：只属于一个世界的资源，例如表世界文章、书籍详情，或里世界帖子和私信会话。
- **世界首页**：表世界为 `/`，里世界草案地址为 `/?world=inner`。
- **共享身份**：一个本地用户唯一的登录主体、公开 handle、头像、资料和关注关系，不因世界不同而复制。
- **协议路由**：ActivityPub、WebFinger、OAuth/API、媒体和 streaming 等机器协议地址，不参与网页翻面；其中联邦协议入口第一阶段对公网关闭。

## 5. 功能需求与验收标准

### R1. 显式世界状态

**用户故事**：作为访问者，我希望链接能明确恢复我所在的世界，同时仍感觉自己在同一个 Rinspace 中。

- 当用户访问 `/` 且没有显式世界状态时，系统应进入表世界。
- 当用户访问双面资源并指定 `world=inner` 时，系统应进入该资源的里世界视图。
- 当用户复制、刷新或在新标签页打开双面资源链接时，系统应恢复链接表达的世界，不得依赖先前 cookie、localStorage 或 history state 才能正确显示。
- 当 URL 对应表世界单面资源时，系统应由资源路径推导其世界；除稳定帖子永久链接 `/p/:id[/slug]` 外，里世界产品网页的规范地址应显式携带 `world=inner`，旧的无参数地址可兼容进入并随即规范化。
- 当 `world` 值未知或格式错误时，系统应安全回到该路径的默认世界并规范化 URL，不得把未知值透传给内部服务。
- 世界状态不得使用 `/community`、`/inner` 等栏目路径把里世界表达成表世界下的一个普通页面。
- `world` 查询参数只属于网页导航；ActivityPub、WebFinger、REST API、streaming、媒体和静态资源请求不得携带或依赖该参数。

> 已确认基线：双面网页使用 `world=inner`；表世界省略 `world=outer`。

### R2. Logo、品牌文字与翻面

**用户故事**：作为用户，我希望用 Logo 翻到当前内容的另一面，用品牌文字回到当前世界首页。

- 当用户点击 `Rinspace` 文字时，系统应导航到当前世界首页：表世界到 `/`，里世界到 `/?world=inner`。
- 当用户在双面资源点击 Logo 时，系统应导航到同一资源的相反世界视图。
- 当用户在单面资源点击 Logo 时，系统应导航到相反世界首页。
- 当双面映射缺失、失效或无权访问时，系统应回到相反世界首页，不得猜测另一个内容对象。
- 当翻面发生时，顶栏应保持视觉稳定，顶栏下方的页面主体执行左右翻转效果。
- 当用户启用 reduced motion 时，系统应使用无 3D 旋转的淡入淡出或即时切换。
- Logo 与品牌文字应是两个独立、可聚焦且具有准确可访问名称的交互目标。
- 第一版不得把 Logo hover 动画当作世界状态反馈或成功判定。

### R3. 世界内导航

**用户故事**：作为用户，我希望普通导航保持在当前世界，只有 Logo 明确执行翻面。

- 当用户点击当前世界的普通导航、账号、标签、搜索结果或分页链接时，系统应保持当前世界。
- 当里世界链接进入本地账号、共享搜索或已绑定标签等双面资源时，系统应保留里世界状态。
- 当表世界链接进入这些双面资源时，系统应保持表世界默认状态。
- 当用户使用浏览器前进或后退时，系统应按历史记录恢复世界、路径、滚动和焦点，不得强制跳回首页。
- 当导航进入 API、媒体或其他机器协议路由时，世界状态不得污染目标 URL。

### R4. 表世界信息架构

**用户故事**：作为读者，我希望表世界安静地突出书籍、博客和知识，而不是继续像混合社区流。

- 当表世界首页渲染时，系统应以书籍、博客、标签和知识发现为主要层级。
- 表世界不得把 Mastodon 时间线或社交发帖框作为首页主内容。
- 讨论、问答、动态的现有入口和兼容路由应保留，但可从首页主层级降级；本期不得删除或合并其历史数据。
- 当旧入口被访问时，系统应继续显示现有内容或明确兼容状态，不得静默改写成 Mastodon 帖子。
- 表世界文章、书籍、写作、标签 Wiki 和知识图谱应继续遵守既有稳定 ID、权限和发布契约。

### R5. 里世界首页和完整社区能力

**用户故事**：作为社区用户，我希望里世界像成熟的实时社交产品，而不是讨论、问答、动态的第四个重复列表。

- 当已登录用户进入里世界首页时，系统应同时提供个性化“推荐”信息流、按关注关系生成的非个性化时间流和发帖入口；不得以实现推荐为由取消用户主动选择关注流的能力。
- 当访客进入里世界时，系统应按站点策略展示可公开访问的本地/探索内容，并明确登录后可用能力。
- 当系统生成个性化推荐时，候选内容应仅来自用户有权查看且已经通过发布与内容治理门禁的 Rinspace 本地帖子。
- 当推荐服务不可用、用户关闭个性化推荐或用户尚无足够信号时，系统应退化到明确标注的非个性化本地热门或时间流，不得阻断里世界首页。
- 每个可互动帖子应按权限提供回复、repost/boost、like/favourite、浏览量、bookmark 和分享。
- 里世界应保留 Mastodon 的引用、媒体、投票、内容警告、可见性、提及、编辑历史、列表、通知、关注请求、屏蔽、静音和举报能力。
- 当动作不适用于受限可见性或当前账号时，系统应准确禁用或隐藏，不得伪造成功。
- 分享应优先调用系统分享能力；不可用时应复制规范网页链接。
- Mastodon 上游没有帖子浏览量；Rinspace fork 应沿用现有 `StatusStat` 计数链路增加独立 `views_count`，并同步扩展 REST Status 契约、前端类型和展示，不得改名复用 favourite、reply、repost 或 quote 计数。
- 第一阶段全部帖子均为本地帖子；浏览量不得使用“全网浏览量”等暗示跨实例统计的文案。

### R6. 一个本地账号，两种内容投影

**用户故事**：作为账号所有者或访客，我希望 `/@username` 的两面属于同一个人，而不是两个同步得不可靠的副本。

- 当访问 `/@username` 时，系统应展示该本地账号的表世界资料与博客、书籍、知识贡献等内容。
- 当访问 `/@username?world=inner` 时，系统应展示同一账号的帖子、回复、媒体和社交活动。
- 两个视图应显示同一个 handle、头像、共享资料和关注/粉丝状态。
- 共享身份头部与各世界内容主体应分别加载；一个世界的内容服务失败不得抹掉共享身份。
- 当用户从任一世界执行关注或取消关注时，两个世界应在同一关系完成后展示相同结果。
- 系统不得为同一本地用户创建两个对外可见账号、两组 follower/following 计数或两套头像资料。
- 当用户输入 `/@username@domain`、搜索远端账号或粘贴远端帖子 URL 时，系统应明确说明第一阶段仅支持 Rinspace 本地社区，不得解析、抓取或自动创建本地副本。

### R7. 统一登录与账号预配

**用户故事**：作为 Rinspace 用户，我希望进入里世界时不再注册或维护第二套密码。

- 当已登录 Rinspace 用户首次进入需要登录的 Mastodon 功能时，系统应通过统一登录完成会话建立，不得要求再次注册、设置 Mastodon 密码或选择第二个 username。
- 当本地用户获得里世界资格时，系统应以稳定 Rinspace subject 预配或绑定唯一 Mastodon User/Account。
- 系统不得依赖 OIDC 默认“冲突时追加数字后缀”的行为生成公开账号。
- 当身份绑定冲突、handle 不合法或账号预配未完成时，系统应阻止发帖和关注写入，进入可诊断的对账状态；不得创建近似账号继续运行。
- 当用户退出 Rinspace 或账号被停用、封禁、删除时，系统应按会话和账号策略同步限制里世界访问。
- Mastodon 的 OAuth 应用、API token 和第三方客户端能力可保留，但不得绕过 Rinspace 的账号状态和合规门禁。

### R8. 共享资料和 handle 生命周期

**用户故事**：作为用户，我希望只维护一次资料，并清楚知道哪些字段会显示在表世界和里世界。

- Rinspace 应是本地 handle、昵称、头像、封面和共享简介的编辑入口与权威来源。
- handle 只应作为当前个人主页的可变导航入口；登录主体、账号绑定、关注关系、帖子作者和其他关键内容必须使用不可变内部 ID，不得以 handle 作为长期身份主键。
- 当共享资料成功变更时，系统应把受支持字段投影到 Mastodon 本地 Account；第一阶段不得因此对外发送 ActivityPub Update。
- 当字段不适合里世界展示或超过共同限制时，系统应在保存前给出明确规则，不得在另一个世界静默截断成不同资料。
- 网站、地点、长 about 等不能直接映射的字段应明确标记为表世界专属，或通过已定义的 Mastodon profile fields 映射。
- 当头像或封面同步时，系统应使用受控对象 URL 或文件传输，不得把浏览器 data URL 当作跨服务永久地址。
- 新增 handle 应满足两个系统共同支持的规则。上线前必须盘点全部现有 handle，并为不兼容项提供人工确认迁移；不得自动生成近似用户名。
- 当第一阶段的本地用户改变 handle 时，系统应通过统一身份映射更新同一个本地 Mastodon Account，不得创建第二个本地身份。
- handle 改名后，旧 `/@username` 不得重定向或揭示新地址；当旧 handle 尚未被重新注册时，该地址应返回 `404`。
- 旧 handle 不得为原账号永久保留，应重新进入与普通 handle 相同的可注册名称池；当它以后被其他账号合法注册时，`/@username` 应表示该名称当时对应的账号，而不得继续关联原账号。
- handle 变更和重新分配不得改变任何既有账号 ID、关注关系、帖子 ID、帖子作者归属或 `/p/:id/:slug` 永久地址。

### R9. 一张关注图

**用户故事**：作为用户，我希望表里世界显示并操作同一份 Rinspace 本地关注关系。

- Rinspace Control Plane 应提供统一关注命令、权限判断、审计和读取入口。
- 本地账号之间的关注、取消关注、锁定账号请求、批准和拒绝应由 Mastodon 关系引擎执行。
- 本地关注关系应在同一生命周期中表达；第一阶段不得创建任何包含远端账号的关系记录。
- 其他系统只能保存可重建投影，不得与 Mastodon 并行接受独立的用户关注写入。
- 既有 Gitea User Follow 应经过幂等迁移和对账后降为兼容投影；无法唯一匹配的关系不得猜测导入。
- Gitea Star、Watch、仓库协作者和内容收藏夹继续保持既有领域语义，不受用户关注图切换影响。
- 当 Mastodon 暂时不可用时，系统不得先在 Rinspace 或 Gitea 假装关注成功；应保留幂等请求并显示可重试状态。

### R10. 帖子永久地址

**用户故事**：作为读者，我希望帖子链接可读，但标题或正文改变后旧链接仍然有效。

- 本地和本实例可展示的帖子网页应支持 `/p/:id/:slug`。
- `:id` 是唯一定位依据；`:slug` 只用于可读性和网页元数据，不参与权限或对象身份判断。
- 当用户访问 `/p/:id` 时，系统应按 ID 找到帖子并导航或规范化到当前 slug。
- 当用户访问 `/p/:id/:wrongSlug` 时，系统应按 ID 正常展示帖子，并以 replace 或规范跳转修正当前 canonical；不得因 slug 错误返回 404。
- 当帖子编辑导致当前 slug 变化时，所有历史 slug 链接应继续按同一 ID 工作。
- 当帖子没有可用于 slug 的正文时，系统应生成稳定、非敏感的类型 fallback，不得把内容警告、私密文本或媒体文件名泄漏到 URL。
- Mastodon 原生浏览器地址 `/@username/:statusId` 应被抛弃；系统不得生成、分享、声明 canonical 或兼容解析这种地址。
- 当用户访问 `/@username/:statusId` 时，系统应返回 `404`，不得查找帖子或重定向到 `/p/:id/:slug`；`/@username` 地址族只用于个人主页及其明确的个人资料子页面。
- 所有帖子卡片、通知、搜索结果、分享、站内链接和网页元数据应统一生成 `/p/:id/:slug`；无 slug 的兼容入口只能是 `/p/:id`。
- ActivityPub status、activity、replies、likes 和 shares 命名空间应保留，但第一阶段不得通过公网开放联邦读取或投递。
- 当对象是 repost/boost 时，系统应明确永久页是展示原帖还是带 repost 上下文；不得把 repost 记录和原帖错误合并成一个 ID。

### R11. 标签的两种视图

**用户故事**：作为用户，我希望同一标签在表世界表示知识，在里世界表示实时话题，而且点击时不会意外翻面。

- Rinspace tag ID 应继续作为共享标签身份和治理权威。
- 每个可双面展示的标签应具有显式、唯一、可审计的 Mastodon Tag 绑定，不得仅凭当前显示名临时猜测。
- 当用户在表世界点击标签时，系统应进入该 tag ID 的表世界知识页。
- 当用户在里世界点击 hashtag 时，系统应进入其里世界时间线并保留里世界状态。
- 当用户在已绑定标签页点击 Logo 时，系统应通过绑定定位同一标签的另一面。
- 当知识标签的名称、slug、别名或合并状态变化时，tag ID 和历史绑定应保持可追踪；不得破坏既有 hashtag 链接。
- 当知识标签名称不符合 Mastodon hashtag 语法时，系统应创建并保存唯一的 Mastodon 安全名称，不得每次动态替换字符后假定无冲突。
- 当本地帖子使用尚未绑定的 hashtag 时，系统可先展示里世界话题，但不得自动创建或篡改 Rinspace 知识标签；该页面在完成绑定前属于里世界单面资源，Logo 回到表世界首页。

### R12. Mastodon 全部本地网页对象与休眠协议边界

**用户故事**：作为里世界用户和维护者，我希望 Rinspace 保留 Mastodon 成熟的本地功能，同时确保未批准的联邦能力不会暗中运行。

- 系统应为账号、帖子、标签、列表、collection、poll、媒体、通知、私信会话、关注请求、设置、屏蔽、静音、举报和管理页面建立明确的路由归属。
- 只有产品网页路由进入世界映射；OAuth、REST API、streaming、媒体和静态资源应绕过世界分流。
- ActivityPub actor/inbox/outbox/followers/following、status activity/replies/likes/shares、context、payload、WebFinger、NodeInfo 和远端解析入口应在公网边缘与应用配置两层关闭，默认拒绝入站和出站联邦通信。
- 第一阶段的后台任务不得执行远端账号解析、远端帖子抓取、联邦 inbox 处理或 delivery 投递；监控应能证明相关队列和网络请求为零。
- 当 Mastodon 上游增加新网页或协议路由时，升级检查应发现未分类路由并阻止静默落入 Rinspace 的 `/:username` 或其他 catch-all。
- 本地账号、锁定账号、不可用账号以及不同帖子可见性应继续遵循 Mastodon 原有授权模型；远端账号与 account move 不进入第一阶段产品流程。
- Rinspace 定制不得把服务器内部数字 ID、私信内容、待批准关系或受限资料暴露到公开页面或客户端日志。

### R13. 路由冲突、canonical 与错误恢复

**用户故事**：作为用户和搜索引擎，我希望相同路径在两个世界中仍有确定结果和正确规范地址。

- `/`、`/@username`、`/search`、`/settings`、`/notifications`、`/about`、`/tags/...` 等重叠路径应在 catch-all 前由显式路由表确定归属。
- 双面页面的 canonical 应包含区分世界所必需的状态；表世界默认地址不得附加冗余 `world=outer`。
- 除 `/p/:id[/slug]` 外，里世界产品页面的 canonical 和新生成站内链接均应包含 `world=inner`；API、OAuth、streaming、媒体与静态资源不得携带该参数。
- 表世界单面页面和里世界 `/p/:id[/slug]` canonical 不得附加无意义的世界状态。
- 当网页请求缺少必要状态但路径只可能属于里世界时，系统应规范化到里世界页面；当路径有歧义时，默认表世界。
- 当另一世界运行时不可用时，翻面应显示可恢复错误并允许返回当前世界，不得造成无限跳转或白屏。
- 世界分流不得覆盖 `/repos/`、`/rin/`、`/quiver/`、`/code/` 等现有明确挂载边界。

### R14. 公开前端、私有服务与 Mastodon fork 的协作

**用户故事**：作为维护者或外部贡献者，我希望能在公开仓库完成可验证改动，而生产秘密和 Mastodon 运维仍留在正确边界。

- `rinspace-web` 应先定义世界状态、双面资源、顶栏行为、公共 API 和确定性 Demo。
- Mastodon fork 应承载里世界 UI、Mastodon 网页路由、帖子永久地址、浏览量扩展和联邦关闭开关，并保留上游 ActivityPub 代码与 AGPL notices。
- 私有 `rinspace` 应承载身份/资料/标签/关注适配、同源路由、密钥、迁移和生产部署，不得复制公开前端源码作为长期分叉。
- 私有仓库应以精确 commit/tag、checksum、SBOM 和 provenance 消费公开前端及 Mastodon fork release，不得消费 `main`、浮动 tag 或本机临时构建。
- 公开 PR 只能使用合成数据和公开契约；不得获得私有仓库、生产数据库、真实账号或部署凭据。
- 跨仓联调应记录三个精确提交和契约版本，但不得因一次联调成功自动发布或部署。
- 工作区契约应在设计确认后把 Mastodon fork 纳入正式活跃仓库清单，并为上游同步、冲突审查和 AGPL 对应源码发布定义流程。

### R15. 数据迁移与渐进发布

**用户故事**：作为维护者，我希望在不破坏当前站点的情况下逐步引入里世界，并能随时回到上一个稳定版本。

- 上线前应匿名盘点并对账账号、handle、资料字段、现有用户关注和标签绑定。
- 身份预配、资料同步、关系迁移和标签绑定应支持幂等重试、审计、差异报告与人工处理队列。
- 新关注写入切换前，应完成一次全量导入、增量追平和双读比对；不得长期双写两个权威图。
- 每个阶段应保持当前表世界可用，并允许独立关闭世界入口、资料同步、关系写入和浏览量；联邦能力必须始终保持关闭。
- 回滚不得删除已经产生的本地 Mastodon 账号、帖子、互动或稳定 ID；第一阶段不得产生远端关系或已对外发布的 ActivityPub actor 身份。
- 生产发布必须使用不可变制品并保留上一版本；不得在生产容器中现场编辑源码或单独替换散落静态文件。

### R16. 中国境内账号与内容治理门禁

**用户故事**：作为平台经营者和社区用户，我希望社区功能上线前具备可执行的账号、内容和申诉机制，而不是只在服务条款里写一句“请遵守法律”。

- 在向用户开放发帖、回复、点赞等信息发布或跟帖评论能力前，系统应完成符合“后台实名、前台自愿”原则的真实身份信息认证；未完成认证的账号不得获得相关写权限。
- 真实身份信息与公开 handle、头像和资料应分层存储和授权，前台不得默认公开后台实名信息。
- 注册、账号资料变更和公众账号信息应经过规则校验，并支持警示、限期改正、限制功能、暂停、关闭和防止违规重新注册等处置状态。
- 系统应提供便捷举报、申诉和处置通知，并保存必要的审核、处置和申诉记录。
- 系统应具备与规模相适应的内容审核、实时巡查、应急处置、违法和不良信息处置及依法报告能力；仅依赖 Mastodon 默认举报队列不视为自动满足中国境内义务。
- 若服务被认定具有舆论属性或社会动员能力，上线跟帖评论新功能、算法推荐或其他受监管能力前，应完成适用的安全评估、备案或其他法定程序。
- 服务协议、账号规则、社区规范、隐私规则和内容处置规则应在开放写入前与实际功能一致，并明确双方权利义务。

### R17. 个人信息与未来联邦门禁

**用户故事**：作为用户，我希望知道本地社区如何处理我的资料和内容，也能行使法定个人信息权利。

- 系统应公开说明登录、实名核验、公开资料、关注、帖子、浏览量和审核日志各自处理的目的、方式、种类、保存期限和权利路径。
- 处理个人信息应遵循合法、正当、必要和诚信原则，并按字段和功能最小化收集。
- 对敏感个人信息、自动化决策、公开个人信息、委托/共同处理和个人信息出境等高风险活动，应在上线前完成并留存个人信息保护影响评估。
- 第一阶段的产品和网络配置不得向其他 Mastodon 实例自动提供、推送或抓取账号、资料、关注和帖子数据。
- 未来任何联邦试验都必须另立规格；若构成向境外提供个人信息，应在启用前满足适用的法定条件、告知和单独同意要求，不得用本期用户协议概括授权。
- 用户应能查阅、更正、复制和依法删除其本地个人信息；系统应区分用户删除与依法需要继续保存、或技术上暂时只能停止其他处理的数据。
- 浏览量不得以公开计数为由长期保存可反查个人的阅读轨迹；去重标识、日志和统计明细应设置最小保存期和访问控制。

### R18. 推荐、排序与浏览量透明度

**用户故事**：作为用户，我希望获得有发现价值的推荐，同时知道时间线为何这样排序，并能关闭个性化推荐。

- 第一阶段应提供由 Rinspace 推荐服务生成的本地帖子个性化信息流；Mastodon 负责帖子与互动事实，推荐服务不得成为帖子、关注或互动的第二权威库。
- 当里世界使用个性化推送、排序精选、检索过滤或其他算法推荐时，系统应显著告知并公开基本原理、目的和主要机制，并明确标识“推荐”与“正在关注”等不同排序来源。
- 系统应提供不针对个人特征的时间顺序或其他非个性化选项，以及便捷关闭个性化推荐的入口。
- 用户应能查看、选择或删除用于推荐的个人标签；关闭后系统应停止相应个性化处理。
- 推荐系统应复用 Rinspace 已有 Gorse 服务和统一用户 subject，并为 Mastodon 本地帖子定义稳定 item ID、可审计候选过滤和互动反馈映射；浏览器不得直接访问 Gorse 或持有其凭据。
- 推荐系统不得制造虚假账号、点赞、评论、repost、浏览量或操纵榜单。
- 浏览量计数规则应公开说明包含的页面、最短可见条件、去重窗口、自有浏览和机器人处理方式。
- 个性化推荐上线前应完成算法告知、关闭、非个性化选项和用户标签管理。安全评估或备案的适用性由负责人结合实际服务属性、规模和内容边界持续判断与跟踪，不作为自动化发布门禁；如负责人关闭“推荐”流，不得连带关闭非个性化关注流。

### R19. 安全、可访问性与运行质量

**用户故事**：作为用户，我希望翻面和统一登录不会降低站点安全、性能与可访问性。

- 两个运行时应使用隔离且最小范围的 cookie、CSRF、OAuth/OIDC state、CSP、CORS 和 service worker 配置。
- 世界查询参数、slug、账号和 hashtag 输入应经过规范化和白名单验证，不得影响上游地址、内部 proxy target 或缓存键安全。
- 顶栏与翻面应支持键盘、屏幕阅读器、焦点恢复、移动端安全区、深浅主题和 reduced motion。
- 同一页面不得同时出现两套可见主导航、两套登录状态或互相覆盖的快捷键。
- 时间线 streaming 中断时应退化为可重试的普通读取；不得拖垮表世界静态阅读。
- 当里世界加载带内容哈希的脚本、样式或公开媒体时，边缘层应保留上游的长期公开缓存语义，不得追加 `no-store` 或使同一发布的温刷新重复下载全部静态依赖。
- 当 Mastodon 页面引用其公开静态资源时，世界路由应把请求交给 Mastodon；不得因遗漏 `/sounds/*`、`/avatars/*`、`/headers/*`、`/media_attachments/*` 或 `/emoji/*` 而返回表世界 404。
- 日志、指标和错误事件不得记录访问 token、OIDC 凭据、帖子私密正文、真实身份材料或完整个人阅读轨迹。
- 世界路由、身份绑定、关系写入、协议 URI 和公开契约都应具有自动化回归门禁；上线前还应进行桌面端、移动端和 reduced-motion 浏览器验收。

## 6. 约束

1. 默认域名仍为 `rinspace.com`，不得为里世界要求用户记忆第二个品牌域名。
2. 表里世界必须共享统一视觉品牌，但可具有明显不同的信息密度与内容节奏。
3. Mastodon fork 及其衍生网络服务继续按 AGPL 要求提供对应源码和许可告知。
4. 公开前端仓库不得包含私有 API 实现、真实数据、密钥、内部域名或生产快照。
5. 第一阶段不得对外发布可被其他实例使用的 ActivityPub actor/status 身份；未来开放联邦前必须单独完成稳定 URI、handle、删除和迁移设计。
6. 任何数据权威切换都必须避免长期双写，并提供对账和回滚/前向修复边界。

## 8. 产品决策记录

已确认：

- 第一阶段严格使用 Rinspace 本地账号和本地帖子。
- 不解析、抓取、接收或展示远端账号与远端帖子。
- 不允许远端关注，不向任何其他实例投递。
- 联邦能力未来如需启用，必须另立规格并重新核查中国法律合规要求。
- 第一阶段包含本地帖子个性化推荐，同时保留可独立选择的非个性化关注/时间流。
- handle 改名后，旧 `/@username` 不得重定向到新地址。
- 旧 handle 不为原账号永久保留；它只是可重新分配的个人主页入口，关键身份和内容继续由固定 ID 标识。
- Mastodon 原生网页帖子地址 `/@username/:statusId` 不进入兼容范围；帖子网页只使用 `/p/:id` 与 `/p/:id/:slug`。

已核查事实：

- 当前 Mastodon `main` 的 `StatusStat`、REST Status 和前端 Status 契约均没有浏览量字段；Rinspace 所需浏览量必须作为 fork 扩展实现。

进入设计的确认基线：

1. 双面网页以 `world=inner` 区分，表世界省略 `world=outer`。
2. Rinspace 是统一管理入口和本地身份权威，Mastodon 是本地社交关注关系的唯一执行者/事实库，Gitea User Follow 降为兼容投影。
3. 里世界同时提供“推荐”和“正在关注”；默认入口、选择记忆和降级行为由设计明确。
4. `views_count` 作为 Mastodon fork 扩展实现；有效曝光、重复浏览、自有浏览和机器人处理由设计给出可审查口径。
